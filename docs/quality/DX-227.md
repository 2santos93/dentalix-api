## Rojo → verde

### Fallo bloqueante de CI: dos asignaciones al mismo hueco

Fuente: https://github.com/2santos93/dentalix-api/actions/runs/39070491360, aserción original de `test/waitlist-offers.int-spec.ts:366`. Una primera ejecución sin cambios pasó (30/30 tests entre billing y waitlist): la carrera depende del scheduler.

Se conserva la regresión con una barrera inmediatamente antes del método real `PrismaAppointmentRepository.create`: las dos peticiones completan los pre-checks antes de sus INSERT. No se falsea ninguna respuesta de persistencia. El test exige una cita real, una entrada SCHEDULED, otra OPEN, y `ConflictException` con el mensaje español original.

El rojo capturó `PrismaClientUnknownRequestError` cuyo SQLSTATE real era **40P01**, no 23P01: dos INSERT se esperan mutuamente al comprobar EXCLUDE. PostgreSQL confirmó `while checking exclusion constraint` en el log. El traductor existente de 23P01 ya era correcto; convertir indiscriminadamente cualquier deadlock en solape habría ocultado el problema.

Corrección mínima en infraestructura: únicamente para altas con `waitlistEntryId`, tomar `pg_advisory_xact_lock` por clínica y profesional antes del INSERT, dentro de la misma transacción. Así las dos asignaciones no entran simultáneamente en EXCLUDE; el INSERT perdedor recibe el 23P01 real que el caso de uso ya traduce a su 409. El candado termina con COMMIT/ROLLBACK, mantiene las fronteras hexagonales y no amplía privilegios. Un control adicional exige que dos horarios contiguos del mismo profesional se confirmen ambos.

### DX-227: rechazo manejado desde el principio y espera observable

El test original creaba `attempt`, esperaba COMMIT y sólo entonces conectaba `.rejects`. Se reprodujo el rechazo no manejado introduciendo temporalmente 100 ms entre COMMIT y la aserción: simula la desplanificación que vuelve intermitente el fallo. Ese retraso diagnóstico **no se conserva**.

El test corregido conecta manejadores de éxito/error en el mismo turno de creación de cada promesa. Una señal explícita confirma la adquisición del candado; `pg_locks` confirma una espera de `transactionid` sobre el XID exacto del holder antes de cancelar/confirmar. No se confunde con esperas de otras suites. La liberación se hace en `finally` y se drenan las promesas. También se comprueba que no se insertó ningún abono.

La transacción de prueba usa `FOR NO KEY UPDATE` y sólo cambia a CANCELLED después de observar la espera. Esto choca con el `FOR SHARE` explícito del repositorio, pero no con el `KEY SHARE` implícito de una FK: evita una falsa prueba del candado del plan.

### Prueba mutante

Se eliminó temporalmente **sólo** el `FOR SHARE` de `PrismaPaymentRepository.insert`, sin cambiar las FK ni otros bloqueos. Comando:

```sh
node_modules/.bin/jest --config test/jest-int.json --runInBand \
  test/billing-rules.int-spec.ts -t 'el abono bloquea el plan'
```

Resultado: exit 1, el abono se cumplió cuando se esperaba rechazo 409. El fichero de producción se restauró automáticamente con `finally`; no hay cambios permanentes en pagos. Evidencia: [billing-mutant.log](dx227-evidence/billing-mutant.log).

### Auditoría de otros tests

Se revisaron las ocurrencias de `rejects`, `setTimeout` y `sleep` en `test/*.int-spec.ts`. Los rechazos diferidos de concurrencia problemáticos eran los de billing; los otros usos revisados conectan el manejador de inmediato o ya estabilizan la promesa. Las dos carreras de `patient-ledgers.int-spec.ts` también usaban pausas de 100–400 ms: ahora utilizan señales y esperan el XID exacto mediante `pg_locks`, conservando las comprobaciones del resumen real.

Los intervalos de sondeo de 10 ms en el helper nuevo, 25 ms en receipt-prefix y 50 ms en lock-order **no son pausas de sincronización**: cada iteración comprueba una condición real de PostgreSQL y falla si ésta no se observa. No quedan pausas fijas para asumir la adquisición de un candado.

## Revisión y límites
